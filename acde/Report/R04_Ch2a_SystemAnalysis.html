Chapter 2 — Part A

System Analysis: Existing & Proposed System

System Analysis

2.1 Existing System — Manual Deployment

The traditional software deployment workflow is a series of manual, error-prone steps performed by a developer directly on a server:

  • SSH into the server; manually install runtime (Node.js, Python, etc.) and all dependencies.
  • Clone the repository and configure environment variables by hand.
  • Start the process using pm2, nohup, or a system service — no containerisation.
  • Manually edit Nginx config, add a server block, test and reload — per application.
  • No unified log interface; logs scattered across journald, app files, or Nginx access logs.
  • Result: High manual effort, "works on my machine" failures, poor visibility.

2.2 Proposed System — ACDE PaaS

ACDE replaces all manual steps with a single API call. The proposed system:

  • Clone: Accepts a Git URL or local path; clones via simple-git or cp -a.
  • Detect & Build: Detects stack (Node/static/Dockerfile); generates Dockerfile if absent; runs docker build.
  • Deploy: Runs docker run with a free host port (OS-probed) or kubectl apply for K8s.
  • Route: Writes an Nginx conf.d snippet; optionally reloads Nginx.
  • Stream: All build logs streamed real-time to the dashboard via SSE (Server-Sent Events).
  • Stop: One-click stop removes the container and the Nginx route atomically.

2.4 Software Requirements Specification (SRS)

Functional Requirements

  • User registration and login with JWT-based stateless authentication.
  • Project creation accepting a Git URL or local path with format validation.
  • One-click deploy triggering the full clone → build → run pipeline asynchronously.
  • Real-time build log streaming to the dashboard (SSE).
  • Project stop: terminates container, removes Nginx route, updates status in DB.
  • Dashboard: deployment counts, system health (Docker + Mongo status), recent projects.

Non-Functional Requirements

  • Security: bcrypt password hashing; JWT with 7-day expiry; input sanitisation on all endpoints.
  • Reliability: K8s deployment falls back to Docker on kubectl failure; port allocator probes OS availability.
  • Performance: SSE log streaming; no polling; fire-and-forget pipeline (202 Accepted).
  • Scalability: Port range configurable (default 31000–31999); K8s resource limits enforced.

2.4 Hardware & Software Constraints

Minimum Hardware

  • CPU: Intel Core i5 / Ryzen 5
  • RAM: 16 GB (Docker + K8s)
  • Storage: 50 GB SSD free
  • Network: Internet for Git clone

Software Dependencies

  • Ubuntu Linux 20.04+
  • Node.js 18+ (runtime)
  • Docker Engine 24+
  • MongoDB 6+ (local/Docker)
  • Nginx (optional, for subdomain)
  • minikube + kubectl (K8s mode)
